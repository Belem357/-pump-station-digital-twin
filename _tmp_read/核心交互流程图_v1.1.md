# 核心交互流程图（修订版）

**项目：小型二供泵房数字孪生监控系统　｜　版本：v1.1　｜　日期：2026-09-23　｜　编制：产品经理（PM）**

> 💡 **使用说明**：以下为文字版逻辑流程，可直接用于绘制 Visio / ProcessOn / Draw.io 流程图。
>
> **v1.1 修订说明**：本文档 v1.0 与《接口规范与数据字典》存在字段名冲突，已按"以接口规范为唯一标准"的原则修订。共 3 处变更：
> 1. 控制指令字段：`device` → `device_id`，`action` → `command`（全文）
> 2. 液位标签：`tank_level_cm` → `tank_level`
> 3. 报警阈值判定方：由**前端判定**改为**后端判定、前端只显示**（流程二）
>
> 变更理由见《接口规范与数据字典 v1.1》第九节变更清单。

---

## 一、三个流程的关系（先看全局）

| 流程 | 谁触发 | 数据往哪个方向走 | 对应 PRD 功能 |
|---|---|---|---|
| 流程一：远程手动启停水泵 | 用户点按钮 | 前端 → 后端 → 模拟器 →（再推回）前端 | 控制下控·单泵手动启停（P0） |
| 流程二：低液位报警与联锁停泵 | 数据越限自动触发 | 模拟器 → 后端 → 前端 | 报警管理·阈值越限报警（P0） |
| 流程三：手自动模式切换 | 用户点开关 | 前端 → 后端 → 模拟器 →（再推回）前端 | 系统设置·手自动模式切换（P1） |

> **一条贯穿全程的铁律**：无论哪个流程，**前端显示的设备状态永远以 WebSocket 推送回来的数据为准**，不以"指令下发成功"为准。原因：指令下发成功 ≠ 设备真的动作了（PLC 侧可能拒绝）。这条规则避免了"UI 显示运行中、实际水泵没转"的假象。

## 二、流程一：远程手动启停水泵（下控操作）

**参与方**：用户 → 前端 → 后端 → 协议解析 → 模拟器（PLC）

| 步骤 | 执行方 | 动作 | 失败时怎么办 |
|---|---|---|---|
| 1 | 用户 | 点击 UI 面板"1#泵 启动"按钮 | — |
| 2 | 前端 | 检查 `sys_mode`：若为 1（自动模式），按钮应已置灰，流程不进入 | 若按钮未置灰却被点击，后端会返回错误码 1006 |
| 3 | 前端 | 弹出二次确认框"确认启动 1#泵？"；确认后按钮进入 Loading 禁用态 | 用户点取消 → 关闭弹窗，按钮恢复，流程终止 |
| 4 | 前端 | `POST /api/v1/control`，Body：`{"device_id":"pump_01","command":"start","operator":"<当前操作人>"}` | — |
| 5 | 后端 | 校验 `device_id`、`command` 合法性；校验当前模式是否允许手动操作 | 非法 → 返回错误码 1002 / 1003 / 1006，跳至步骤 11 |
| 6 | 后端 | 记录操作日志（操作人 + 时间戳）——PRD 1.3 安全性要求 | 日志写入失败不阻断主流程，但需记入后端错误日志 |
| 7 | 后端 | 经协议解析写 Modbus 线圈 `00001 = 1` | 通信超时 → 返回错误码 1001，跳至步骤 11 |
| 8 | 模拟器 | 执行启动逻辑，更新保持寄存器 `40003 = 1`（即 `pump_01_status = 1`） | — |
| 9 | 后端 | 返回 `200 OK {"code":0,"msg":"success","timestamp":...}` | — |
| 10 | 前端 | 收到 code=0：按钮解除 Loading、恢复可用。**此刻不改状态显示**，等待步骤 12 | — |
| 11 | 前端 | （失败分支）收到非 0 错误码：按钮解除 Loading，按错误码表弹出对应中文提示 | — |
| 12 | 后端 | 下一个 500ms 周期，WebSocket 推送全量数据，其中 `pump_01_status = 1` | — |
| 13 | 前端 | 依据推送数据：UI 状态变为"运行中(绿色)"；3D 节点 `pump_01_motor` 开始旋转 | — |

**停止流程**：与上完全相同，仅 `command` 改为 `"stop"`，写入线圈 `00002 = 1`，最终 `pump_01_status` 变为 0，3D 水泵停止旋转。

**耗时要求**（PRD 验收标准）：步骤 4 → 步骤 9（指令响应）须 **< 1 秒**；步骤 8 → 步骤 13（状态同步）须 **< 500ms**。

## 三、流程二：低液位自动报警与联锁停泵

**参与方**：模拟器 → 协议解析 → 后端 → 前端

> **⚠️ v1.1 关键修订**：v1.0 写的是"前端判断：比对阈值，确认触发低液位报警"。现改为**后端判定阈值**。理由：若前后端各算一套，会出现"后端已联锁停泵、前端还没报警"的状态不一致。统一由后端算、前端只负责呈现。

| 步骤 | 执行方 | 动作 |
|---|---|---|
| 1 | 模拟器 | 液位数据下降至 24cm（低于 25cm 阈值） |
| 2 | 协议解析 | 每 200ms 采集一次，读到 `tank_level = 24.0`，交给后端 |
| 3 | 后端 | **阈值判定**：`tank_level < 25` 成立 → 置 `alarm_level_low = 1`，`alarm_active + 1` |
| 4 | 后端 | **写入报警记录**：生成一条 `type = level_low`、`level = critical`、`status = active` 的记录，含触发值 24.0 与阈值 25.0，存入数据库（供 `/api/v1/alarms` 查询） |
| 5 | 后端 | **联锁动作**：向模拟器写入停泵线圈，切断所有运行中的水泵（防止水泵空转烧毁） |
| 6 | 后端 | WebSocket 推送全量数据：`tank_level = 24.0`、`alarm_level_low = 1`、`pump_01_status = 0`、`pump_02_status = 0` |
| 7 | 前端 | 读到 `alarm_level_low = 1`，执行三件事：① 右上角弹出红色 Toast"【警告】水箱液位过低(24.0cm)"；② 播放警报音；③ 3D 节点 `tank_body` 材质变红闪烁 |
| 8 | 前端 | 读到 `pump_0x_status = 0`，停止对应 3D 水泵旋转动画，UI 状态改为"已停止" |
| 9 | 模拟器 | 液位回升（进水阀补水），`tank_level` 逐渐上升 |
| 10 | 后端 | 判定 `tank_level > 30`（**回升阈值高于触发阈值，形成防抖**）→ 置 `alarm_level_low = 0`，将步骤 4 那条报警记录更新为 `status = recovered`，填入 `time_end` |
| 11 | 后端 | 若 `sys_mode = 1`（自动模式），按自动逻辑重新启动主泵；若为手动模式，**不自动启泵**，等待人工操作 |
| 12 | 前端 | 读到 `alarm_level_low = 0`：Toast 变为"已恢复"或自动消除、停止警报音、3D 恢复正常颜色 |

**防抖设计说明**（验收清单 4.4 要求"液位在阈值附近波动时，水泵不发生频繁启停，30s 防抖"）：

- **双阈值（回差）**：触发阈值 25cm，恢复阈值 30cm。液位在 25～30cm 之间波动时，报警状态不翻转。
- **时间防抖**：即使液位跌破 25cm，也需**连续 30 秒**低于阈值才真正触发报警与联锁；瞬时尖峰（如传感器抖动）不触发。
- **启泵间隔**：联锁停泵后，**30 秒内不接受任何启泵指令**（后端返回错误码 1008），防止频繁启停损坏电机。

> 这三重防抖均由**后端**实现，前端不参与判定。

**超压报警（pipe_pressure > 0.8MPa）的差异**：流程与上相同，但 **不联锁停泵**，只报警。理由见《接口规范与数据字典 v1.1》第十节待决策事项 #3（超压停泵会导致高层住户突然断水，真实运维中通常先报警由人工判断）。**此项仍需 PM 最终确认。**

## 四、流程三：手自动模式切换

**参与方**：用户 → 前端 → 后端 → 模拟器

| 步骤 | 执行方 | 动作 |
|---|---|---|
| 1 | 用户 | 点击顶部导航栏"自动模式"开关 |
| 2 | 前端 | 弹出二次确认"确认切换为自动模式？切换后手动启停/调速将被屏蔽"（属下控操作，PRD 1.3 要求二次确认） |
| 3 | 前端 | `POST /api/v1/control`，Body：`{"device_id":"sys","command":"set_mode","value":1,"operator":"<操作人>"}` |
| 4 | 后端 | 校验 value ∈ {0,1} → 经协议解析写入保持寄存器 `40011 = 1` |
| 5 | 模拟器 | 切换内部运行模式，返回成功 |
| 6 | 后端 | 返回 `200 OK {"code":0}` |
| 7 | 后端 | 下一周期 WebSocket 推送 `sys_mode = 1` |
| 8 | 前端 | **依据推送回来的 `sys_mode`**（不是依据步骤 6 的成功响应）：所有手动启停/调速按钮置灰禁用；UI 显示"当前：自动模式" |
| 9 | 模拟器 | 自动模式下，按液位自动执行启停与轮换逻辑（如液位低时启动备用泵、两泵定期轮换以均衡磨损） |
| 10 | 前端 | 自动模式下仅做状态展示，不提供手动干预入口 |

**切回手动模式**：`value` 传 0，步骤同上。切回后手动按钮恢复可用，PLC 停止自动逻辑。

**互斥逻辑要求**（PRD 验收标准"模式切换即时生效，互斥逻辑正确"）：

- 自动模式下收到手动指令 → 后端返回错误码 **1006**，前端提示"当前为自动模式，手动操作已被屏蔽"
- 模式切换生效前已下发的指令 → 正常执行完毕，不中断
- **双保险**：前端置灰按钮（用户体验层）+ 后端拒绝指令（安全层）。不能只靠前端置灰，因为绕过前端直接调接口仍能下发指令

## 五、异常与边界场景（补全）

> v1.0 只画了正常路径（happy path）。验收清单 4.4 要求测试异常场景，故本节补全。

| 场景 | 触发条件 | 系统行为 | 依据 |
|---|---|---|---|
| WebSocket 断开 | 前端 15 秒内未收到任何消息（含心跳） | 顶部红色横幅"⚠ 数据连接断开，正在重连…"；3D 模型保持最后状态；所有控制按钮置灰；每 3 秒自动重连 | 验收清单 4.2；接口规范 5.3 |
| 重连成功 | 前端重新连上后端 | 清除横幅、恢复按钮；后端首次推送必须为全量数据，确保状态一致 | 接口规范 5.3 |
| 模拟器未启动 | 后端连不上模拟器 | `/api/v1/health` 返回 `plc_connected: false`；所有控制指令返回错误码 2002；前端提示"数据服务未就绪" | 接口规范 6.6、七 |
| 非法 device_id | 请求传入 `pump_03` 等不存在的设备 | 后端返回错误码 1002，**不得崩溃** | 验收清单 4.4 |
| 非法 command | 请求传入 `restart` 等未定义指令 | 后端返回错误码 1003 | 验收清单 4.4 |
| value 越界 | `set_freq` 传入 60（超过 50Hz 上限） | 后端返回错误码 1004，前端提示数值超出范围 | 接口规范 七 |
| 缺少必填字段 | 未传 `device_id` | 后端返回错误码 1005 | 接口规范 七 |
| 频繁下发指令 | 同一设备 2 秒内重复下发 | 后端返回错误码 1008；前端按钮 Loading 期间本就禁用，属双保险 | PRD"有 Loading 防抖" |
| 水泵故障状态 | `pump_0x_status = 2` | 该泵 3D 模型红色闪烁；对其下发 `start` 返回错误码 1007；UI 显示"故障" | 接口规范 七 |
| 通信中断报警 | 后端连续 5 秒读不到模拟器数据 | 生成 `type = comm_lost` 报警记录；前端提示数据连接异常 | 接口规范 6.5 |

## 六、绘图建议（给做 Visio / Draw.io 的人）

- **泳道图**最合適：五条泳道分别是「用户 / 前端 / 后端 / 协议解析 / 模拟器」，能一眼看出每个动作由谁执行、数据往哪流。
- **三个流程各画一张**，不要挤在一张图里。
- **异常分支用红色虚线**，正常路径用实线，便于评审时聚焦。
- 每个流程标注**耗时要求**（如"步骤 4→9 须 < 1s"），这是验收时的判定依据。
- 导出 PNG 后插入 Word，同时在文档里保留文字版（便于检索和版本对比）。
