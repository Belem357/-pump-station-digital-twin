## 二、3D 模型节点命名规范

> 用途：前端通过代码按名字查找模型节点，名字必须与三维建模时**严格一致**。

| 节点名称 | 对应设备 | 动画 / 交互要求 | 驱动它的数据标签 | 来源 |
|---|---|---|---|---|
| tank_body | 水箱主体 | 静态 | — | 原字典 |
| tank_water_surface | 水箱水面 | Y 轴缩放映射液位 | tank_level | 原字典 |
| pump_01_motor | 1#泵电机 | Y 轴旋转，转速 ∝ 频率 | pump_01_freq、pump_01_status | 原字典 |
| pump_02_motor | 2#泵电机 | Y 轴旋转，转速 ∝ 频率 | pump_02_freq、pump_02_status | 原字典 |
| valve_inlet | 进水总阀 | Z 轴旋转映射开度 | valve_inlet_opening（见第三节，**待决策**） | 补齐 |
| pipe_main_out | 出水主管道 | UV 滚动模拟水流方向 | pipe_flow_speed（见第三节，**待决策**） | 补齐 |
| pump_01_body | 1#泵泵体 | 报警时材质变红闪烁 | pump_01_status | 补齐 |
| pump_02_body | 2#泵泵体 | 报警时材质变红闪烁 | pump_02_status | 补齐 |

> **⚠️ 待决策（第 5 周前定）**：`valve_inlet` 和 `pipe_main_out` 这两个节点，原数据字典里没有任何标签能驱动它们——模型建出来也不会动。两个选项：
> - **选项 A（推荐）**：先做成静态装饰，不接数据。省工，不影响 PRD 任何 P0/P1 功能。
> - **选项 B**：补 `valve_inlet_opening`（阀门开度 %）和 `pipe_flow_speed`（水流速度）两个标签，需要传感器工程师在模拟器里一并造出来。
>
> 本文档暂按选项 B 把标签列在第三节，但标注为"可选"。若选 A，第 5 周前把这两行删掉即可。
>
> **⚠️ 新增说明**：`pump_01_body` / `pump_02_body` 是本次补齐的。原因：验收清单要求"3D 模型对应设备红色闪烁"，而原字典只有电机节点（`pump_0x_motor`）——电机在旋转，让旋转的部件变红闪烁视觉上不清晰，需要一个独立的泵体节点承载报警变色。请三维工程师确认模型层级中已有此节点。

## 三、实时数据标签字典

### 3.3 系统与报警

| 标签名 (Key) | 数据类型 | 单位 | 说明 | 正常范围 | 来源 |
|---|---|---|---|---|---|
| sys_mode | Int | — | 系统模式 | 0=手动, 1=自动 | 原字典 |
| alarm_active | Int | — | 当前生效报警数量（0 表示无报警） | 0 ~ 10 | **补齐**（验收清单要求报警状态可视化） |
| alarm_level_high | Int | — | 液位过高报警标志 | 0=正常, 1=报警 | **补齐** |
| alarm_level_low | Int | — | 液位过低报警标志（tank_level < 25） | 0=正常, 1=报警 | **补齐**（PRD P0） |
| alarm_pressure_high | Int | — | 超压报警标志（pipe_pressure > 0.8） | 0=正常, 1=报警 | **补齐**（PRD P0） |
| ws_connected | Int | — | 前后端连接状态（前端本地维护，不经后端） | 0=断开, 1=已连接 | **补齐**（验收清单要求断网容错提示） |

> **说明**：`alarm_*` 系列是"报警标志位"，由后端根据阈值计算后随数据一起推送，**前端不再自己判断阈值**。原因：原流程图写的是"前端比对阈值确认触发报警"，这会导致前后端各算一套、报警状态不一致。统一改为后端算、前端只负责显示。此变更需在第 2 周对齐会上向前后端双方确认。

## 四、Modbus 地址映射表（新增）

> **为什么必须有这张表**：协议解析工程师的工作是"把 PLC 寄存器地址翻译成标签名"（例如 `40001` → `tank_level`）。原四份文档里没有这张表，等于让他凭空猜地址，**无法开工**。
>
> **⚠️ 本表地址为建议值，需传感器工程师在模拟器中实际建点后回填确认**。确认后本表即为双方契约，不得单方修改。

| Modbus 地址 | 寄存器类型 | 对应标签名 | 数据类型 | 缩放系数 | 备注 |
|---|---|---|---|---|---|
| 40001 | 保持寄存器 | tank_level | Float | ÷10 | 模拟器存整数 855 → 实际 85.5 cm |
| 40002 | 保持寄存器 | pipe_pressure | Float | ÷1000 | 存 420 → 实际 0.420 MPa |
| 40003 | 保持寄存器 | pump_01_status | Int | ×1 | 0/1/2 |
| 40004 | 保持寄存器 | pump_01_freq | Float | ÷10 | 存 450 → 45.0 Hz |
| 40005 | 保持寄存器 | pump_01_current | Float | ÷10 | 存 125 → 12.5 A |
| 40006 | 保持寄存器 | pump_01_temp | Float | ÷10 | 存 456 → 45.6 ℃ |
| 40007 | 保持寄存器 | pump_02_status | Int | ×1 | 0/1/2 |
| 40008 | 保持寄存器 | pump_02_freq | Float | ÷10 | — |
| 40009 | 保持寄存器 | pump_02_current | Float | ÷10 | — |
| 40010 | 保持寄存器 | pump_02_temp | Float | ÷10 | — |
| 40011 | 保持寄存器 | sys_mode | Int | ×1 | 0=手动, 1=自动 |
| 40012~40013 | 保持寄存器（双字） | today_kwh | Float32 | ×1 | 32 位浮点占两个寄存器，高字在前 |
| 40014 | 保持寄存器 | valve_inlet_opening | Float | ÷10 | 可选，见第二节待决策 |
| 40015 | 保持寄存器 | pipe_flow_speed | Float | ÷100 | 可选，见第二节待决策 |
| 00001 | 线圈 | pump_01_cmd_start | Bool | — | 写 1 启动 1#泵（后端下发） |
| 00002 | 线圈 | pump_01_cmd_stop | Bool | — | 写 1 停止 1#泵 |
| 00003 | 线圈 | pump_02_cmd_start | Bool | — | 写 1 启动 2#泵 |
| 00004 | 线圈 | pump_02_cmd_stop | Bool | — | 写 1 停止 2#泵 |
| 00005 | 线圈 | sys_cmd_set_mode | Bool | — | 配合 40011 切换手自动 |
| 40020 | 保持寄存器 | pump_01_freq_setpoint | Float | ÷10 | 变频调速目标值（后端写入） |
| 40021 | 保持寄存器 | pump_02_freq_setpoint | Float | ÷10 | 同上 |

**缩放系数说明**：Modbus 寄存器只能存整数，所以小数要放大后传输、读取时再缩小。例如液位 85.5cm，模拟器里存 855，协议解析读出来后 ÷10 还原成 85.5。**这个换算由协议解析工程师负责，后端和前端拿到的永远是还原后的真实值。**

**采集周期**：协议解析每 **200ms** 从模拟器读取一次；后端每 **500ms** 向前端推送一次全量数据（推送频率低于采集频率是有意的，避免前端渲染压力过大）。

## 五、WebSocket 实时推送

### 5.1 连接地址

```
ws://<后端IP>:8000/ws/realtime
```

### 5.2 推送频率与内容

后端每 **500ms** 推送一次**全量**数据（不是增量）。全量推送虽然数据量略大，但前端无需维护状态合并逻辑，对零基础团队更友好。

```json
{
  "timestamp": 1695000000,
  "data": {
    "tank_level": 85.5,
    "pipe_pressure": 0.42,
    "today_kwh": 12.6,
    "pump_01_status": 1,
    "pump_01_freq": 45.0,
    "pump_01_current": 12.5,
    "pump_01_temp": 45.6,
    "pump_02_status": 0,
    "pump_02_freq": 0.0,
    "pump_02_current": 0.0,
    "pump_02_temp": 28.3,
    "sys_mode": 0,
    "alarm_active": 0,
    "alarm_level_high": 0,
    "alarm_level_low": 0,
    "alarm_pressure_high": 0,
    "valve_inlet_opening": 100.0,
    "pipe_flow_speed": 1.2
  }
}
```

> `timestamp` 为 Unix 秒级时间戳（10 位整数）。前端可用它判断数据新鲜度。

### 5.3 心跳与断线重连（新增）

> **为什么要有这一节**：验收清单第 4.2 节明确要求"WebSocket 断开时，UI 提示'数据连接断开'，模型保持最后状态"。原文档没有任何心跳/重连约定，前后端无从实现。

- **心跳**：后端每 **10 秒**发送一条 `{"type":"ping","timestamp":<秒>}`；前端收到后回 `{"type":"pong"}`。
- **判定断开**：前端若 **15 秒**内未收到任何消息（含心跳），判定连接断开。
- **断开后前端行为**（验收要求）：
  1. 页面顶部显示红色横幅"⚠ 数据连接断开，正在重连…"
  2. 3D 模型**保持断开前最后状态**，不清零、不停止动画
  3. 所有控制按钮**置灰禁用**（避免下发指令但无反馈，造成误判）
  4. 本地标记 `ws_connected = 0`
- **自动重连**：前端每 **3 秒**尝试重连一次，重连成功后清除横幅、恢复按钮、标记 `ws_connected = 1`。
- **重连后数据处理**：后端在重连成功后的**第一次推送必须为全量数据**，确保前端状态与后端一致（不依赖前端缓存补齐）。

## 六、RESTful API 接口定义

### 6.1 接口总览

| 方法 | 路径 | 用途 | 来源 |
|---|---|---|---|
| POST | /api/v1/control | 下发设备控制指令 | 原文档 |
| GET | /api/v1/status | 获取当前全量状态（一次性快照） | **补齐** |
| GET | /api/v1/history | 查询历史数据（画折线图用） | **补齐**（验收清单 4.2 要求历史曲线） |
| GET | /api/v1/alarms | 查询报警记录列表 | **补齐**（PRD P1 要求报警记录查询） |
| GET | /api/v1/health | 服务健康检查 | **补齐**（便于联调排错） |

> **为什么必须补 GET 接口**：原文档只有一个 POST 控制接口。但验收清单要求"历史曲线：图表组件正确渲染过去 1 小时的压力和液位折线图"、PRD 要求"报警记录查询"——这两项**物理上没有接口可调用**，不补则功能无法实现。

### 6.2 POST /api/v1/control —— 下发控制指令

**Request Body**

```json
{
  "device_id": "pump_01",
  "command": "start",
  "value": 0,
  "operator": "张三"
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| device_id | String | 是 | 设备标识，取值见下表 |
| command | String | 是 | 指令类型，取值见下表 |
| value | Number | 视指令而定 | `set_freq` / `set_mode` 时必填，其余可省略或传 0 |
| operator | String | 是 | 操作人姓名。**PRD 1.3 安全性要求"记录操作人与时间戳"**，原接口无此字段，本次补齐 |

**device_id 合法取值**

| device_id | 含义 |
|---|---|
| pump_01 | 1#泵 |
| pump_02 | 2#泵 |
| sys | 系统全局（用于模式切换） |

**command 合法取值**

| command | 含义 | value 要求 | 适用 device_id |
|---|---|---|---|
| start | 启动 | 忽略 | pump_01、pump_02 |
| stop | 停止 | 忽略 | pump_01、pump_02 |
| set_freq | 设定目标频率 | 0.0 ~ 50.0（Hz） | pump_01、pump_02 |
| set_mode | 切换手自动模式 | 0=手动, 1=自动 | sys |

**Response（成功）**

```json
200 OK
{ "code": 0, "msg": "success", "timestamp": 1695000000 }
```

**Response（失败）**

```json
400 Bad Request
{ "code": 1001, "msg": "PLC communication timeout", "timestamp": 1695000000 }
```

> **⚠️ 字段名统一说明**：原《核心交互流程图》中写的是 `{device:"pump_01", action:"start"}`，与《接口规范》的 `{device_id, command}` **冲突**。现统一为 **`device_id` + `command`**，流程图中的 `device` / `action` 写法**作废**。交互流程图文档需同步修订（见第九节）。

### 6.3 GET /api/v1/status —— 获取当前状态快照

**用途**：前端首次加载页面时调用一次，立即拿到当前状态，**不必等 WebSocket 第一次推送**（避免首屏空白 500ms）。

**Request**：`GET /api/v1/status`（无参数）

**Response**

```json
200 OK
{
  "code": 0,
  "msg": "success",
  "timestamp": 1695000000,
  "data": { ...同 5.2 的 data 结构... }
}
```

### 6.4 GET /api/v1/history —— 查询历史数据

**用途**：绘制验收清单要求的"过去 1 小时压力和液位折线图"。

**Request 参数**（Query String）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| tags | String | 是 | 要查询的标签名，多个用逗号分隔，如 `tank_level,pipe_pressure` |
| start | Int | 是 | 起始时间，Unix 秒级时间戳 |
| end | Int | 是 | 结束时间，Unix 秒级时间戳 |
| interval | String | 否 | 采样间隔，默认 `1m`；可选 `10s`/`1m`/`5m`。间隔越小数据点越多 |

**示例**：`GET /api/v1/history?tags=tank_level,pipe_pressure&start=1694996400&end=1695000000&interval=1m`

**Response**

```json
200 OK
{
  "code": 0,
  "msg": "success",
  "series": {
    "tank_level": [
      { "t": 1694996400, "v": 82.1 },
      { "t": 1694996460, "v": 83.4 }
    ],
    "pipe_pressure": [
      { "t": 1694996400, "v": 0.41 },
      { "t": 1694996460, "v": 0.42 }
    ]
  }
}
```

> `t` = timestamp（秒），`v` = value（数值）。用短字段名是为了减少传输体积——1 小时按 10 秒采样有 360 个点，字段名省一个字符就省不少流量。
>
> **数据量上限**：单次查询返回点数不超过 **2000 点**。若按请求的 interval 计算会超出，后端自动放大 interval 并在响应中返回实际使用的值（新增字段 `actual_interval`）。

### 6.5 GET /api/v1/alarms —— 查询报警记录

**用途**：PRD P1 功能"报警记录查询：历史报警列表含时间、设备、类型、状态（已恢复/未恢复），支持按时间/设备筛选"。

**Request 参数**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| start | Int | 否 | 起始时间戳，缺省为最近 24 小时 |
| end | Int | 否 | 结束时间戳 |
| device_id | String | 否 | 按设备筛选，如 `pump_01`；缺省为全部 |
| status | String | 否 | `active`（未恢复）/ `recovered`（已恢复）；缺省为全部 |
| page | Int | 否 | 页码，默认 1 |
| page_size | Int | 否 | 每页条数，默认 20，最大 100 |

**Response**

```json
200 OK
{
  "code": 0,
  "msg": "success",
  "total": 57,
  "page": 1,
  "page_size": 20,
  "items": [
    {
      "alarm_id": "A20260923001",
      "time_start": 1695000000,
      "time_end": 1695000180,
      "device_id": "tank",
      "type": "level_low",
      "level": "warning",
      "status": "recovered",
      "value_at_trigger": 24.0,
      "threshold": 25.0,
      "message": "水箱液位过低(24.0cm)"
    }
  ]
}
```

**type 合法取值**

| type | 含义 | 触发条件 |
|---|---|---|
| level_low | 液位过低 | tank_level < 25 cm |
| level_high | 液位过高 | tank_level > 140 cm |
| pressure_high | 超压 | pipe_pressure > 0.8 MPa |
| pump_fault | 水泵故障 | pump_0x_status = 2 |
| comm_lost | 通信中断 | 后端连续 5 秒读不到模拟器数据 |

**level 取值**：`warning`（警告，黄色）/ `critical`（严重，红色，触发联锁停泵）

### 6.6 GET /api/v1/health —— 健康检查

**用途**：联调排错用，确认后端服务活着、且能连上模拟器。

**Response**

```json
200 OK
{
  "code": 0,
  "status": "ok",
  "plc_connected": true,
  "ws_clients": 2,
  "uptime_sec": 3600,
  "timestamp": 1695000000
}
```

| 字段 | 说明 |
|---|---|
| plc_connected | 后端能否连上模拟器（false 说明是协议解析或模拟器的问题，不是前端的问题） |
| ws_clients | 当前有几个前端页面连着 |
| uptime_sec | 服务已运行秒数 |

> 这个接口在联调时非常有用：数据传不过来时，先访问它，就能判断问题出在后端之前还是之后，避免六个人互相甩锅。

## 七、错误码表（新增）

> **为什么必须补**：验收清单第 4.4 节要求"非法输入：API 传入非法 device_id 或 command 时，返回明确错误码而非崩溃"。原文档只定义了 1 个错误码（1001），无法区分错误类型，前端也就无法给用户准确提示。

| code | HTTP 状态 | 含义 | 前端应显示的提示 |
|---|---|---|---|
| 0 | 200 | 成功 | 无需提示 |
| 1001 | 400 | PLC 通信超时 | "控制指令下发失败：设备通信超时，请重试" |
| 1002 | 400 | device_id 非法 | "控制指令下发失败：未知设备" |
| 1003 | 400 | command 非法 | "控制指令下发失败：未知指令" |
| 1004 | 400 | value 超出范围 | "控制指令下发失败：数值超出允许范围（如频率须在 0~50Hz）" |
| 1005 | 400 | 缺少必填字段 | "控制指令下发失败：请求参数不完整" |
| 1006 | 409 | 模式冲突：自动模式下拒绝手动指令 | "当前为自动模式，手动操作已被屏蔽" |
| 1007 | 409 | 设备处于故障状态，拒绝启动 | "该水泵处于故障状态，无法启动" |
| 1008 | 429 | 指令过于频繁（防抖） | "操作过于频繁，请稍后再试" |
| 2001 | 500 | 后端内部错误 | "系统内部错误，请联系维护人员" |
| 2002 | 503 | 模拟器未连接 | "数据服务未就绪，请检查模拟器是否启动" |

**错误响应统一格式**

```json
{
  "code": 1002,
  "msg": "invalid device_id: pump_03",
  "timestamp": 1695000000
}
```

> **前端处理原则**：任何非 0 的 code 都要给用户**看得懂的中文提示**（用上表第四列），不能直接把 `msg` 英文原文弹给用户，也不能静默失败。所有下控按钮在等待响应期间保持 Loading 禁用态（PRD 要求"有 Loading 防抖"）。

## 八、控制指令完整时序（修订版）

> 本节修订自原《核心交互流程图》流程一，主要变更：字段名统一、报警判定方由前端改为后端。

**场景：用户点击"1#泵 启动"**

| 步骤 | 执行方 | 动作 |
|---|---|---|
| 1 | 用户 | 点击 UI 面板"1#泵 启动"按钮 |
| 2 | 前端 | 弹出二次确认框"确认启动 1#泵？"，按钮进入 Loading 禁用态（PRD 安全性要求） |
| 3 | 前端 | 用户确认后，`POST /api/v1/control` `{"device_id":"pump_01","command":"start","operator":"张三"}` |
| 4 | 后端 | 校验字段合法性（device_id / command / 当前模式）→ 非法则返回对应错误码，流程终止 |
| 5 | 后端 | 记录操作日志（operator + timestamp，PRD 1.3 要求） |
| 6 | 后端 | 通过协议解析写 Modbus 线圈 `00001 = 1` |
| 7 | 模拟器 | 执行启动逻辑，更新保持寄存器 `40003 = 1`（pump_01_status） |
| 8 | 后端 | 返回 `200 {"code":0,"msg":"success"}` |
| 9 | 前端 | 收到成功响应，按钮恢复可用；**但状态显示不在此刻改**，等下一步 |
| 10 | 后端 | 下一个 500ms 周期推送全量数据，其中 `pump_01_status = 1` |
| 11 | 前端 | 收到推送，UI 状态变为"运行中(绿色)"，3D 模型 `pump_01_motor` 开始旋转 |

> **关键设计（步骤 9 的说明）**：前端收到 200 后**不要立刻**把状态改成"运行中"，而要等 WebSocket 推送回来的真实状态。原因：指令下发成功 ≠ 设备真的启动了（可能 PLC 侧拒绝）。以推送回来的 `pump_01_status` 为唯一真相，可避免"UI 显示运行、实际没转"的假象。这一点原流程图的表述容易被误解为"收到 200 就改状态"，本次明确修订。

**报警判定职责划分（修订）**

| 环节 | 原流程图写法 | v1.1 修订为 |
|---|---|---|
| 阈值比对 | 前端比对阈值，确认触发报警 | **后端**比对阈值，计算 `alarm_*` 标志位后随数据推送 |
| 前端职责 | 判断 + 显示 | **仅显示**：读 `alarm_*` 字段决定弹 Toast、播放警报音、3D 变红闪烁 |
| 修订理由 | — | 前后端各算一套会导致报警状态不一致（例如后端已联锁停泵、前端还没报警）。统一由后端判定，前端只做呈现 |

## 十、仍需 PM 决策的事项（不阻塞第一周）

| # | 待决策事项 | 建议 | 最迟决策时间 |
|---|---|---|---|
| 1 | `valve_inlet` / `pipe_main_out` 是接数据还是做静态装饰 | 选 A：先做静态装饰，不接数据（PRD 无此要求，省工） | 第 5 周开工前 |
| 2 | Modbus 地址映射表中的地址是否为最终值 | 由传感器工程师在模拟器建点后回填，PM 确认并更新版本号 | 第 2 周对齐会 |
| 3 | 超压（pressure > 0.8MPa）是否触发联锁停泵 | 建议**只报警不停泵**。原因：超压停泵会导致高层住户突然断水，真实运维中通常先报警由人工判断。低液位则**必须联锁停泵**（防止水泵空转烧毁） | 第 7 周做报警功能前 |
| 4 | 历史数据存储方案 | 建议 InfluxDB（时序数据库，专为这类场景设计）。若安装困难，第 9 周可临时降级为 SQLite + 定时写入，功能不变 | 第 9 周开工前 |
| 5 | `today_kwh`（今日耗电量）如何计算 | 建议由后端根据各泵电流与运行时长累加计算，每日 00:00 归零；不要求模拟器直接提供 | 第 8 周做看板前 |
| 6 | 液位过高阈值定为多少 | 本文档暂定 140cm（水箱总高 150cm，留 10cm 安全余量）。PRD 只规定了过低阈值 25cm，未规定过高阈值，需 PM 补定 | 第 7 周做报警前 |
