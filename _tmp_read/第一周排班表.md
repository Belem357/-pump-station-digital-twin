# 泵房数字孪生项目 · 第一周工作排班表

**项目：小型二供泵房数字孪生监控系统　｜　版本：v1.2　｜　更新日期：2026-09-23　｜　编制：产品经理（PM）**

> **基本前提**：团队零基础、总工期约 3 个月（12 周）、**每周三上午向导师演示一次**。
>
> **节奏定调（重要）**：三个月时间充裕，第一周**不追求做出能演示的功能**，而是「**准备与学习周**」——每人把工具装好、跟着官方教程跑通一个最小例子、搞懂自己负责的是整条链路的哪一环。第一周周三的演示内容是"环境就绪情况 + 项目计划 + 各自学到了什么"，**不是**演示一个能动的系统。
>
> **关于一周节奏**：演示固定在**周三上午**，所以一周的循环是「**周四开工 → 下周三上午演示**」。下表用"星期几"表示节奏、不绑定具体日期，每周循环都适用。
>
> **六人角色**：传感器与设备模拟、协议解析、后端、三维模型、前端、产品经理。**不单设"AI 工程师"岗位**——现有分工方案与四份文档中均无此岗位、也无 AI 问答类功能需求；设备与数据模拟相关职责由传感器与设备模拟工程师承担。如后续确需新增 AI 功能，再单独评估工作内容与工期。
>
> **版本说明**：v1.2 在 v1.1 基础上，依据"三个月工期不必赶工"重新定调——第一周由"打通数据链"降级为"准备与学习"，并补充 12 周总览。

## 〇、先看几个词（小白词典）

下面这些词本周会反复出现，先用大白话解释一遍，看不懂随时回来查：

| 术语 | 大白话解释 |
|---|---|
| 数字孪生 | 真实设备在电脑里的"实时分身"，真实设备一变化，3D 模型跟着变 |
| 模拟器 / PLC 模拟器 | 一个软件，假装自己是一台真实的控制柜和水泵，能产生数据、能接收指令。我们没有真泵房，就用它顶替 |
| Modbus | 工业设备之间"说话用的语言"，最常用也最简单的一种通信协议 |
| 协议解析 | 把模拟器用 Modbus"说"出来的数据，翻译成网页能看懂的统一名字（例如把"寄存器 40001"翻译成"tank_level 液位"） |
| 后端 / FastAPI | 跑在电脑后台的一段程序，负责存数据、把数据推给网页；FastAPI 是搭这段程序的工具 |
| WebSocket | 一条"后台主动、持续往网页推数据"的通道，像直播，数据一变就推过去 |
| 前端 / Three.js | 网页这一侧；Three.js 是让网页能显示 3D 模型的工具库 |
| glb / glTF | 3D 模型的文件格式；Blender 建好模型导出成 glb，网页才能加载 |
| Blender | 免费的 3D 建模软件 |
| 点表 / I-O 点表 | 一张清单，列出"有哪些数据点、每个点叫什么名、什么单位、范围多少" |
| 联调 | 把各人做好的模块拼到一起，测试能不能配合工作 |

## 一、整个项目 12 周怎么走（先看清全局，就不慌了）

三个月分成四个阶段，每个阶段结束都有一个"能给导师看的成果"。第一周只是起点，后面时间很宽裕：

| 阶段 | 周次 | 阶段目标 | 阶段末能给导师看什么 |
|---|---|---|---|
| **一、打地基** | 第 1～2 周 | 装好环境、跑通各自的最小例子、统一字段规范 | 六人环境全部就绪，各自能演示一个"Hello World"级小例子 |
| **二、通数据** | 第 3～4 周 | 把"模拟器 → 协议解析 → 后端 → 前端 3D"这条线打通 | **3D 泵房能显示，改模拟器液位，网页水箱跟着升降**（第一个真正的里程碑） |
| **三、加功能** | 第 5～8 周 | 依次加：启停控制、水泵动画与变频调速、报警、数据看板 | 能远程启停水泵、水泵会转、低液位会报警变红、看板数值齐全 |
| **四、补完善** | 第 9～12 周 | 历史曲线、手自动模式、性能优化、界面美化、文档定稿、彩排 | 完整系统 + 全套文档，通过最终验收 |

**逐周细目**：

| 周次 | 这一周主要做什么 |
|---|---|
| 第 1 周 | **准备与学习**：装工具、跑官方入门教程、PM 统一字段命名规范 |
| 第 2 周 | **各自最小 demo**：模拟器能出数、协议能读到数、后端能推数、三维建出水箱、前端能转方块 |
| 第 3 周 | **第一次串线**：数据从模拟器一路传到网页，网页上先显示出液位数字（还不用 3D） |
| 第 4 周 | **3D 动起来**：加载完整 glb 模型，液位数字驱动水箱水面升降 ← 里程碑 |
| 第 5 周 | **启停控制**：网页点按钮 → 指令传到模拟器 → 泵状态翻转 → 网页同步 |
| 第 6 周 | **动画与调速**：水泵旋转动画、频率滑块调速、转速随频率变化 |
| 第 7 周 | **报警功能**：低液位 / 超压报警，3D 设备红色闪烁，报警记录列表 |

| 第 9 周 | **历史数据**：接入时序数据库，做过去 1 小时的压力 / 液位折线图 |
| 第 10 周 | **手自动模式**：模式切换、自动模式下屏蔽手动按钮、PLC 按液位自动控泵 |
| 第 11 周 | **联调与优化**：整体联调、帧率与加载速度优化、界面美化、断网容错 |
| 第 12 周 | **收尾**：彩排、四份文档定稿、最终验收演示 |

## 二、第一周的唯一目标：六个人都"入门"，而不是"出活"

一句话目标：

> **每个人把自己角色的工具装好，跟着官方教程跑通一个最小的例子，并且能说清楚"我这一环在整条数据链路的哪个位置、上游给我什么、我要给下游什么"。**

为什么第一周只定这个目标？因为团队零基础，最大的风险不是"做得慢"，而是"环境装不上、卡在一个报错上三天没人管"。第一周把环境和认知这两关过了，后面 11 周才走得顺。这一周做不出任何能演示的功能，是完全正常的，不用焦虑。

整条数据链路长这样，每个人对号入座，就知道自己在哪一环：

```
[传感器: 造数据] → [协议解析: 读出来+翻译成统一名字] → [后端: 存起来+推给网页] → [前端: 收到数据+让3D动起来]
                                                                              ↑
                                                              [三维: 提供 3D 模型文件]
                            [产品经理: 定规矩(字段名)、盯进度、对接口、备演示 —— 贯穿全程]
```

**本周投入参考**：按课程/实训节奏，每人每天投入 1～3 小时即可，**不要熬夜赶工**。

## 四、第一周逐日排班表

> 标注说明：【必达】= 本周底线，做不完周三演示时会露怯；【学习】= 跟教程练手，重在理解不求完美；【可选】= 有余力再做，做不完完全不影响。

### Day 1（周四）· 启动 + 装环境

当日目标：全员知道这周要干什么；每人开始装自己的工具。

- **产品经理**
  - 【必达】开一个 全员启动会，讲三件事：① 项目要做什么（用第一节那张链路图讲）；② 这周只求"入门"不求"出活"，别慌；③ 12 周总览，让大家知道自己在整个计划里的位置
  - 【必达】把第七节的《统一字段命名表》发到群里，说明"以后所有文档和代码都以这张表为准"
  - 【学习】通读四份现有文档，记下自己看不懂的地方（不用全懂，能提出问题是好事）
- **传感器**：【必达】下载并打开 Modbus 模拟器（推荐 ModRSsim2，免安装、对零基础友好），能手动改数值就算成功
- **协议解析**：【必达】装好 Python；【学习】`pip install pymodbus`，照着官方文档跑通一个"读取寄存器"的示例
- **后端**：【必达】装好 Python 和 FastAPI；【学习】照着 FastAPI 官方首页的 5 行示例，让浏览器打开一个显示 "hello" 的页面
- **三维**：【必达】装好 Blender；【学习】跟着 Blender 官方"甜甜圈教程"或任意入门视频，建出一个立方体
- **前端**：【必达】装好 Node.js 和 VSCode；【学习】照着 Three.js 官网第一个示例，让屏幕中央出现一个会转动的方块

> 装环境卡住是这周最正常的事。**卡住超过 1 小时就别硬磕**，记下来发给 PM，周四晚上或周五集中解决，或者群里互相问。

### Day 2（周五）· 继续入门 + 集中解决装不上的问题

当日目标：把昨天没装好的补上；每人开始理解自己这一环。

- **产品经理**：【必达】收集"谁卡在哪"，组织一次集中答疑；【学习】开始起草周三演示讲稿的框架
- **传感器**：【学习】熟悉模拟器的寄存器概念，搞清楚"保持寄存器 / 线圈"分别是什么；【可选】在模拟器里手动建一个数值，设想它就是"水箱液位"
- **协议解析**：【学习】搞懂 Modbus 的"地址"和"数值"怎么对应；【可选】尝试读出传感器昨天建的那个数值
- **后端**：【学习】搞懂"REST 接口"和"WebSocket"的区别（前者是问一句答一句，后者是持续推）；【可选】写一个每 2 秒打印一次时间的死循环，理解"定时推送"的感觉
- **三维**：【学习】继续跟建模教程，熟悉移动 / 旋转 / 缩放和"命名对象"在哪操作；【可选】建一个半透明长方体，想象它是水箱
- **前端**：【学习】搞懂 Three.js 的"场景 / 相机 / 渲染器"三件套分别是什么；【可选】给昨天那个方块换颜色、换转速

### Day 3（周六）· 互相讲一遍（本周最关键的一天）

当日目标：每人用 5 分钟讲清楚"我在链路哪一环、上游给我什么、我要给下游什么"。**这一步比写代码更重要**——零基础团队最容易出的问题就是各干各的、最后拼不起来。

- **全员**：【必达】每人准备 5 分钟口头说明，回答三个问题：
  1. 我这一环负责什么？（一句话）
  2. 我的"输入"是谁给的、长什么样？
  3. 我的"输出"要给谁、长什么样？
- **产品经理**：【必达】主持这场 1 小时的"互相讲一遍"会；把六个人的输入输出串起来，检查有没有"接不上"的地方（比如协议解析说要输出 JSON，但后端以为收到的是 Modbus 原始数据——这就是接不上）
- **产品经理**：【必达】会后整理出一份《链路接口草表》：谁给谁、给什么格式。这份东西下周（第 2 周）会变成正式约定
- **各角色**：【可选】继续练手，补自己还没跑通的部分

> 这一天的产出不是代码，是**共识**。周六这一步做扎实了，第 3 周串线时能少踩一半的坑。

### Day 4（周日）· 自由练习 + 补进度

当日目标：弹性时间，谁慢谁补，不安排新任务。

- **全员**：【学习】按自己的节奏继续跟教程；昨天"互相讲一遍"时发现自己理解错的地方，重新捋一遍
- **产品经理**：【可选】把四份文档里发现的问题整理成清单（不用改文档，先记下来），周三演示时可以跟导师提一句"我们发现文档里有几处不一致，计划下周统一"
- **三维 / 前端**：【可选】这两个角色可以提前聊一下模型怎么交付（glb 文件怎么给、命名怎么对），为第 4 周做准备

> 这天不强制投入。如果前几天已经顺利，周日可以休息。三个月的项目，可持续的节奏比一时的冲刺重要得多。

### Day 5（周一）· 内部对齐会

当日目标：确认六人环境全部就绪；确认下周（第 2 周）每人要做的"最小 demo"是什么。

- **产品经理**：【必达】主持 45 分钟对齐会，逐项过：
  - 每个人的工具装好了吗？跑通最小例子了吗？还有什么卡着？
  - 周六整理的《链路接口草表》有没有遗漏或矛盾？
  - **下周每人要交出什么**（见下方"第 2 周预告"），逐个确认对方听懂了
- **全员**：【必达】到场，说清自己的状态和下周计划
- **产品经理**：【必达】会后发一份《第 2 周任务清单》到群里，白纸黑字，避免口头说完就忘

**第 2 周每人要做的"最小 demo"**（本周先知道，不用做）：

| 角色 | 第 2 周要交出的最小 demo |
|---|---|
| 传感器 | 模拟器里建好 `tank_level`（水箱液位，0～150cm），能手动改数值 |
| 协议解析 | 一段小程序，能连上模拟器、把 `tank_level` 读出来打印在屏幕上 |
| 后端 | 一个 WebSocket 通道，能每 500ms 往外发一条测试数据（先随便发个固定数字） |
| 三维 | 一个水箱模型（半透明长方体），按规范命名 `tank_body`、`tank_water_surface`，导出 glb |
| 前端 | 一个 Three.js 页面，能加载一个 glb 文件并显示出来 |
| 产品经理 | 《接口约定 v1》正式定稿；第 2 周演示脚本 |

### Day 6（周二）· 彩排（全员到场）

当日目标：把周三要讲的内容走一遍，确保不冷场、不超时。

- **产品经理**：【必达】写好演示讲稿，下午带全员彩排一遍。讲稿建议 5～8 分钟，结构是：
  1. 项目是什么（1 分钟，用那张链路图讲）
  2. 12 周计划（1 分钟，让导师看到我们有规划）
  3. 本周做了什么：六人环境就绪 + 各自跑通了最小例子（2 分钟，可以让每人说一句）
  4. 我们的发现与下周计划（1～2 分钟，包括"发现文档字段名有不一致，已统一"）
- **全员**：【必达】到场彩排，确认自己那一句能讲利索；准备好"如果导师问我技术细节，我怎么答"
- **各角色**：【可选】把自己跑通的小例子截图或录屏存好，演示时万一场地网络不好，可以用截图代替现场跑

### Day 7（周三上午）· 导师演示（全员到场）

当日目标：向导师汇报第一周的准备情况，并拿到导师对 12 周计划的反馈。

- **产品经理**：【必达】主讲。**本周没有能动的系统可以演示，这是正常的**——你展示的是"团队就绪 + 计划清晰 + 已经发现并解决了文档不一致的问题"，这本身就是合格的启动周成果
- **全员**：【必达】到场；导师问到技术细节时由对应角色回答（比如问"你们用什么协议"，由协议解析的人答"Modbus TCP"）
- 建议主动向导师问三个问题（拿到反馈，后面 11 周才不跑偏）：
  1. 我们的 12 周节奏，您觉得哪里需要调整？
  2. 第 4 周做出"3D 水箱随液位升降"，这个里程碑的验收标准您认可吗？
  3. 除了 PRD 里的功能，您还希望看到什么？
- 演示结束后（周三下午）：全员花 30 分钟复盘，PM 记录导师反馈，据此调整第 2 周任务清单

## 七、现在就统一：字段命名表（附大白话解释）

**为什么第一周就要做这件事？** 我核对了你现有的四份文档，发现同一个东西在不同文档里有两个名字。如果不趁早统一，等第 3 周开始串线时，后端按 A 写、前端按 B 写，数据一定对不上，到时候排查会很痛苦。现在改只是改几个字，成本几乎为零。

**发现的问题（举例）**：

| 同一个东西 | 文档里出现的两种写法 | 统一为 |
|---|---|---|
| 控制指令里的设备编号 | 流程图文档写 `device`；接口文档写 `device_id` | **`device_id`** |
| 控制指令里的动作 | 流程图文档写 `action`；接口文档写 `command` | **`command`** |
| 水箱液位 | 流程图文档写 `tank_level_cm`；接口文档写 `tank_level` | **`tank_level`**（单位仍是 cm） |

**PM 周四直接复制下面这三张表发群里，全员以此为准**：

**1）控制指令格式**（网页向后端发指令时用；`device` / `action` 这种写法作废）

```
POST /api/v1/control
{ "device_id": "pump_01", "command": "start", "value": 0 }
command 只能取四个值：start（启动）、stop（停止）、set_freq（设频率）、set_mode（切模式）
```

**2）实时数据标签**（第 2 周先打通 `tank_level` 一个，其余按 12 周计划逐步接入）

| 标签名 | 含义 | 单位 | 范围 | 哪一周接入 |
|---|---|---|---|---|
| tank_level | 水箱液位 | cm | 0～150 | 第 2～4 周（主线） |
| pipe_pressure | 出水总管压力 | MPa | 0～1.0 | 第 8 周 |
| pump_01_status | 1#泵状态 | — | 0=停止 / 1=运行 / 2=故障 | 第 5 周 |
| pump_01_freq | 1#泵频率 | Hz | 0～50 | 第 6 周 |
| pump_01_current | 1#泵电流 | A | 0～20 | 第 8 周 |
| sys_mode | 系统模式 | — | 0=手动 / 1=自动 | 第 10 周 |

> 注：`pump_02` 系列标签（2#泵的状态、频率、电流）目前文档里只在 WebSocket 示例中出现过、但标签字典里没定义。第 5 周做启停功能前，PM 需把 `pump_02_status`、`pump_02_freq`、`pump_02_current` 补进字典。

**3）3D 模型节点命名**（三维和前端必须严格一致，全英文小写 + 下划线，差一个字母前端就找不到模型）

| 节点名 | 对应设备 | 动画要求 |
|---|---|---|
| tank_body | 水箱主体 | 静态 |
| tank_water_surface | 水箱水面 | 高度随液位升降 |
| pump_01_motor | 1#泵电机 | 旋转，转速随频率 |
| pump_02_motor | 2#泵电机 | 旋转，转速随频率 |
| valve_inlet | 进水总阀 | 旋转映射开度 |
| pipe_main_out | 出水主管道 | 模拟水流方向 |

> 注：`valve_inlet`（进水阀）和 `pipe_main_out`（出水管道）这两个节点，目前的数据标签字典里没有任何数据能驱动它们——也就是说模型建出来了也不会动。第 6～8 周需要 PM 决定：是给它们补数据标签，还是先做成静态装饰。这件事不急，第 5 周前定下来就行。
