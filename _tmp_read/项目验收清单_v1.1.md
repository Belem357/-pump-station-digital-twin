# 项目验收清单（补全版）

**项目：小型二供泵房数字孪生监控系统　｜　版本：v1.1　｜　日期：2026-09-23　｜　编制：产品经理（PM）**

> **使用说明**：每周三内部对齐时逐项打勾，未通过项当场指定修复人与复检时间。
>
> **v1.1 修订说明**：v1.0 共 20 项检查，但存在两类问题——① 部分检查项无判定依据（如"返回明确错误码"，却没说哪些错误码算明确）；② 缺少对新补接口和约定的检查（历史查询、报警查询、心跳重连、操作日志）。本次补至 **41 项**，每项都标注了"判定依据"和"建议验收周次"，可直接照着测。
>
> **打勾符号**：✅ 通过　｜　⚠️ 部分通过（需注明缺什么）　｜　❌ 未通过　｜　⬜ 未测试
>
> **验收周次说明**：本清单覆盖全部 12 周。标注"第 N 周"表示该功能计划在那一周做出来、也就在那一周验收。**第一周（准备与学习周）不验收任何功能项**，只验收第 0 节的"环境与共识就绪"。

## 第 7 节 · 未通过项跟进表

> 每次验收后，把未通过项填进这张表。v1.0 只给了一个示例行，v1.1 补充了填写规范。

| 问题描述 | 影响哪个检查项 | 修复方案 | 责任人 | 复检时间 | 状态 |
|---|---|---|---|---|---|
| （示例）停泵延迟达 3s | 2-3 | 检查后端推送频率，调整为 500ms/次 | 后端工程师 | 周四 12:00 | ❌ 待修复 |
| | | | | | |
| | | | | | |
| | | | | | |

**填写规范**：

1. **问题描述**写现象，不写猜测的原因（"停泵延迟 3s"而非"后端可能有 bug"）
2. **影响哪个检查项**必须填编号（如 2-3），便于追踪是哪一项没过
3. **责任人**填具体角色，不填"大家"
4. **复检时间**必须是具体时间点，不能写"尽快"
5. **状态**只用三种：❌ 待修复 / 🔧 修复中 / ✅ 已复检通过
6. 已通过的行**不要删除**，保留作为项目过程记录，最终交付时一并提交
