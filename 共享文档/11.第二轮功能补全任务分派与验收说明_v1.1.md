## 一、这一轮要解决什么

第一轮我们把数据链路打通了：模拟器造数 → 协议解析 → 后端 → WebSocket → 3D 场景，全流程能跑。但组长复查了一遍 PRD 功能矩阵（F1~F10）和代码，发现三类问题：

1. **PRD 里写明了、但没做成的 P0 功能**——比如 F1 要求 3 个预设视角，实际只有 1 个；F4 要求"点击 3D 模型下发指令"，实际 3D 点不了设备。**P0 不做则项目不通过验收。**
2. **代码写好了、却永远触发不了的"死代码"**——最典型的是泵故障：报警规则、错误码 1007、前端红闪分支、3D 红色信号灯、验收项 4-23 全都写好了，**但模拟器里没有任何入口能让一台泵变成故障状态**，所以这一整条链路等于不存在。
3. **"一用一备"的核心逻辑没实现**——`devices.json` 的讲解词承诺"定期轮换以均衡磨损"，但代码里永远优先启 1#泵，2#泵几乎不会单独运行；也没有 1#泵坏了自动切备泵的逻辑。
4. **3D 场景视觉简陋**——`泵房.glb` 里 **0 张贴图**、12 个材质全是纯色，前端**没开环境反射**，所以不锈钢和设备看着像塑料积木；控制柜已经有显示屏和三个指示灯的节点，但**是空壳不亮**；进出水总管在模型里**不显眼**，看不出哪根进、哪根出。选题是「供水机房参观、供水系统及设备讲解」，**门面问题就是功能问题**。

**本轮目标：把上面四类补上，做到 10-14 周三能当场演出来。**

只补功能与视觉、**不动架构**。数据链路、接口格式、测点地址全部保持不变（唯一例外见 3.5 节的 `devices.json` 文案）。

> 📌 **三压分区 + 6 台泵**（高中低三区、每区一用一备）是本轮的**下一轮**议题，属范围变更，**本轮不启动**，见第八节与《12.三压分区改造方案》。

### 3.1 A1 ｜① 传感器与设备模拟 ｜补泵故障注入

**要做什么**

给模拟器加一个**键盘按键**入口，按一下让 1#泵进入故障状态（`pumpStatus[0] = 2`），再按一下恢复。

**为什么**

`pumpStatus` 的语义定义了 `0=停止 / 1=运行 / **2=故障**`，但全后端搜下来**没有任何一行代码把它赋值为 2**，点表里也没有故障注入点。后果是这条链路全程无法触发：

| 环节 | 位置 | 现状 |
|---|---|---|
| 故障状态位 | `sensorSim.py:241` 注释定义了 2 | 无入口产生 |
| 故障报警 | `alarmEngine.py:63` `pump_01_fault` | 永不触发 |
| 后端拒绝启动 | `main.py:429` 错误码 1007 | 永不返回 |
| 前端红闪 | `scene.html:723` `if (status === 2)` | 死代码 |
| 3D 信号灯 | GLB 里的 `信号灯红` 材质 | 用不上 |
| **验收项 4-23** | "故障泵拒绝启动 → 1007" | **无法验收** |

**怎么做**

- 用键盘按键（建议 `F`），**不新增 Modbus 测点**，因此不需要改《03 接口规范》，也不需要通知 ② 协议解析
- 按键后要在控制台打印一行中文提示（如 `[注入] 1#泵 置为故障(2)`），方便答辩现场看清发生了什么
- 支持两台泵分别注入（如 `F` 管 1#、`G` 管 2#）
- **故障状态要能持续**，不要下一拍就被别的逻辑改回去（这正是 A2 要修的）

**验收标准**

1. 按 `F` 后，`pump_01_status` 读出来是 `2`
2. 后端 `/api/v1/alarms` 出现 `pump_fault` 类型报警
3. 此时下发启动指令，后端返回错误码 **1007**
4. 前端 3D 上 1#泵**红色闪烁**
5. 再按一下 `F` 能恢复（状态回到 0 或 1）

**自测要求**

用 `linkCheck.py` 或 `QModMaster` 手动读一次 `pump_01_status` 寄存器，确认能读到 2；再把 5 条验收标准各走一遍，**把结果贴到提交说明里**。

**交付物**

`代码/backend/sensorSim.py` + 一段说明"按哪个键、怎么恢复、怎么验证"（发群里就行，不用正式文档）。

### 3.2 A2 ｜① 传感器与设备模拟 ｜修 `autoControl` 覆盖故障的 bug

**要做什么**

`sensorSim.py:313` 的 `state["pumpStatus"][0] = 1` 是无条件赋值，必须加上"该泵不是故障状态"的判断。

**为什么（这条很重要）**

`autoControl` 里 `runningCount = sum(1 for status in state["pumpStatus"] if status == 1)` —— **只数状态为 1 的泵**。所以当 1#泵是故障（2）时，`runningCount` 数不到它。此时如果液位 ≥ 90（`LEVEL_AUTO_START`），代码会执行：

```python
state["pumpStatus"][0] = 1     # ← 把故障泵直接改写成"运行"！
```

**结果是：自动模式下故障会凭空消失，报警跟着消失。** 现在因为造不出故障所以没暴露，但 A1 一旦做完，这个 bug 立刻会被踩到 —— 答辩现场按了 `F`，几秒后故障自己没了，非常尴尬。

**怎么做**

- 把第 313 行（以及同段的 316-317 行启 2#泵的逻辑）改为：**跳过状态为 2 的泵**
- 顺带处理：如果 1#泵故障、2#泵在待机，自动模式应当**启 2#泵顶上**（这就是 B1 的"故障切换"，可以先留个 TODO，B1 一起做）
- 在第 322 行"停泵"逻辑里确认：**故障状态的泵不参与停泵改写**（故障还在，不能因为液位低就把它变成 0）

**验收标准**

1. 自动模式下按 `F` 让 1#泵故障 → **过 30 秒故障依然存在**，报警不消失
2. 手动模式下按 `F` → 同样不被改写
3. 液位降到 ≤ 40 触发自动停泵后，故障泵的状态**仍是 2**（没被改成 0）

**自测要求**

必须走"自动模式 + 故障注入 + 等 30 秒以上"这条路径，因为 bug 只在自动模式下触发。**贴 30 秒前后的两次读数对比**到提交说明里。

**交付物**

`代码/backend/sensorSim.py` + 上面那组前后对比读数。

> ⚠️ **A1 和 A2 由同一个人（① 号）做，建议一次改完一起自测**——先修 A2 再加 A1，否则自测必然踩坑。

### 3.5 B1 ｜① 主责 / ⑥ 定文案 / ③ 改数据文件 ｜备泵轮换 + 故障自动切换

**要做什么**

在 `autoControl` 里补两条泵房真实逻辑：**定期轮换**（均衡两台泵磨损）和**故障自动切换**（1#坏了 2#顶上）。

**为什么**

`devices.json` 里 2#泵的讲解词是这么写的：

> "与 1#泵一用一备：正常时一台运行，另一台备用；高负荷（自动模式下液位过高）时两台同时投入，**定期轮换以均衡磨损**。"

但实际 `autoControl`（`sensorSim.py:297-325`）只有三条规则：

```
液位 ≥ 90            →  启 1#泵        ← 永远优先 1#
液位 ≥ 130 且已运行1台 →  启 2#泵
液位 ≤ 40            →  全部停泵
```

**问题一：不会轮换。** 停泵后下次还是从 1#开始，2#泵几乎不单独运行。**备用泵长期闲置在泵房运维里是大忌**——泵会锈死、卡死，真要用的时候起不来。"一用一备"的意义就在于此。

**问题二：不会故障切换。** 1#泵坏了，2#泵不会自动顶上。

**问题三：文档承诺了、系统没做。** 讲解时讲给参观者听，会和系统实际行为对不上。

**怎么做**

- **轮换**：按累计运行时长或启停次数轮换主用泵。最小实现：记录每台泵的累计运行秒数，自动启泵时选**累计运行时间短的那台**作为主用
- **故障切换**：自动模式下若主用泵状态为 2（故障），直接启另一台
- 轮换规则要简单可解释（答辩会被问"你怎么决定的"），不要去搞复杂的加权算法
- **⭐ 请按"可复用"的形式写（第三轮要用，成本几乎为零）**：把"选哪台泵当主用"抽成**独立函数，入参是泵索引列表**，不要继续写死 `[0]` / `[1]`。理由见《12.三压分区改造方案》第五节——第三轮要扩到三区 6 台泵，写成可复用的形式能把 ① 的工作量从 4~6 天压到 2~3 天
- **⚠️ 必须与 A2 一起做**：A2 修的是"故障泵被改写"，B1 加的是"故障时换泵"，两者改的是同一个函数，分开做会冲突

**验收标准**

1. 自动模式下反复启停几轮，**两台泵的运行时间大致均衡**（不能总是一台跑）
2. 1#泵注入故障后，自动模式下 **2#泵自动启动**，供水不中断
3. 1#泵故障期间，`pump_01_status` 保持 2（不被改写）—— 这条与 A2 共用
4. 轮换逻辑不引起**频繁启停**（PRD 要求防抖，不能液位一动就换泵）

**关于 `devices.json` 文案**

轮换和故障切换做完后，`devices.json` 里那句讲解词就**名副其实**了。由 **⑥ PM 复核文案口径**（讲解词要能对着系统实际行为讲），**③ 后端负责改数据文件**（`devices.json` 归后端维护）。

**自测要求**

跑一轮 5~10 分钟的自动模式，**记录两台泵各自的累计运行时间**（打印出来）贴提交说明。这是证明"真的在轮换"的唯一证据。

**交付物**

`代码/backend/sensorSim.py` + 两台泵的累计运行时间对比。

### 3.6 B2 ｜⑤ 主责 / ④ 确认节点名 ｜Raycaster 点 3D 设备弹讲解卡片

**要做什么**

让 3D 场景里的设备**能被鼠标点击**，点了弹出讲解卡片（设备名称、作用、传感器型号、实时数值）。

**为什么**

课程选题是「**供水机房参观、供水系统及设备讲解**」。而讲解场景最核心的交互 —— 点设备看讲解 —— 现在是缺的：全文件搜不到一处 `Raycaster`，讲解卡片只能从左侧列表点。`模型升级路线图.md` 第 4 条也把这条列为"最核心的交互缺着"。

**关键：后端数据已经做好了，不用等任何人。** `GET /api/v1/devices` 已经返回完整的讲解数据（`代码/backend/devices.json`），前端只是没把它接到 3D 上。

**怎么做**

- 用 `THREE.Raycaster` + `pointerdown` 事件做拾取
- 可点击的节点取自 `devices.json` 的 `node3d` 字段（例：`tank_body` / `tank_water_surface`、`pump_01_motor` / `pump_01_body`、`pipe_main_out`、`valve_inlet`）
- **注意**：点水泵时可能命中 `pump_01_motor` 或 `pump_01_body`（两个节点），**要做父子/同名归组**，别出现"点电机弹一个卡片、点泵体弹另一个"
- 点空白处关闭卡片
- 悬停时高亮（可选，但有明显提升）
- 卡片里如果有启停按钮，**必须走 A4 的二次确认**
- 注意不要和 OrbitControls 的拖拽冲突：**判断"按下和抬起的位移小于阈值"才算点击**，否则旋转视角时会误触发卡片

**④ 三维要做什么**

只需**确认节点名清单**与 `devices.json` 的 `node3d` 字段一致。**不需要重新导出模型**。如果发现某个设备在模型里的名字与清单不符，报给 ⑤ 并同步 ⑥。

**验收标准**

1. 点水箱 → 弹卡片，显示"水箱（蓄水池）"及其实时液位
2. 点 1#泵 → 弹对应卡片，**不会因为点到电机壳/泵体而弹错**
3. 点管道/地面 → 不弹卡片（或弹空态）
4. 旋转视角时不误触发卡片
5. 卡片里的数值**跟着 WebSocket 实时更新**（不是打开时的快照）
6. 点空白处能关闭

**自测要求**

逐台设备点一遍，**每个设备截一张卡片图**；另外专门测一次"按住拖拽旋转"确认不误弹。

**交付物**

`代码/frontend/scene.html` + 各设备卡片截图。

### 3.7 D1 ｜⑤ 前端 ｜操作面板"活"起来

**要做什么**

把 3D 里那个控制柜从"空壳"变成真正的操作面板：显示屏显示实时数据，三个指示灯反映系统状态。

**好消息：不需要重新建模。** `泵房.glb` 里**已经有** `控制柜柜体` / `控制柜柜门` / `控制柜把手` / `控制柜显示屏` / `控制柜指示灯1/2/3` 这 7 个节点，而且有三个现成材质：`信号灯红` / `信号灯绿` / `信号灯黄`。缺的只是"让它活起来"——这是"泵房看着不像真泵房"里**最便宜、见效最快**的一刀，也正好消除了 ② 号角色本轮的空闲。

**怎么做**

- **显示屏**：用 `THREE.CanvasTexture` 把一块 2D canvas 贴到 `控制柜显示屏` 的材质上，每 500ms 重绘一次（与 WebSocket 推送同频）。内容建议：液位、出水压力、今日电量，**都带单位**
- **三个指示灯**：分别绑定"系统正常（绿）/ 自动模式或预警（黄）/ 有未恢复报警（红）"。GLB 已有三个信号灯材质，直接换材质或改 `emissive` 即可
- **本轮面板不做操作入口**（已决策"只显示"），指令仍从侧边栏和 3D 点击卡片下发

**验收标准**

1. 显示屏上能看到液位/压力/电量，数值跟着 WebSocket 更新
2. **断开后端 → 显示屏不能继续显示一个冻结的假数值**（要显示"离线"或明显的失效态）
3. 用 A1 的按键注入报警 → 红灯亮
4. 切到自动模式 → 黄灯亮
5. 1920×1080 下显示屏上的字**能看清**（别做成马赛克）

**自测要求**：三张截图（正常 / 报警红灯 / 自动模式黄灯）；D1 改动前后的 FPS 对比。

**交付物**：`代码/frontend/scene.html` + 三张截图 + FPS 对比。

### 3.8 D2 ｜④ 三维 Blender ｜进出水口做明确

**要做什么**

让"水从哪进、从哪出"一眼看懂：进出水总管加法兰与阀件（④），⑤ 配合加流向标注。

**为什么**

GLB 里其实**已经有** `进水总管` / `进水手轮` / `进水阀体` / `进水阀杆` / `出水口外接` / `出水手轮` / `出水横管1/2` / `出水阀体`。问题是它们在整体里**不显眼**，看一眼模型分不清哪根是进、哪根是出。

**怎么做**

- **④**：给进出水总管端部加**法兰盘**（视觉上有个明确的"接口"），把阀件做得更清楚
- **⑤**：加**流向标注**——沿管道方向的箭头动画（流动粒子或贴图流动），以及"进水""出水"文字标牌（CanvasTexture 做 sprite）
- 建议：**进水用冷色（蓝）、出水加压后用暖色**，一眼区分
- **④ 可选顺手做（半天，④ 本轮有富余）**：把**公共隔膜气压罐**也建出来（圆柱 + 封头，简单构件）。本轮的恒压变频逻辑不做，所以罐**先作为模型与讲解内容存在**——10-14 演示时能说"罐已就位，恒压逻辑下一轮实现"，比"以后再说"有说服力。**理由与返工风险分类见《12.三压分区改造方案》第十节**

**验收标准**

1. 看一眼模型就能指出哪根是进水总管、哪根是出水总管
2. 能看到水流方向（箭头或流动效果）
3. 泵运行时流动效果**跟着启停**（停泵就不流），不要一直流
4. 重新导出后**节点名仍正确**（跑过两条校验命令）

**自测要求**：两张截图（停泵 / 运行）+ 节点名校验命令的输出。

**交付物**：`泵房.glb`（新）+ `代码/frontend/scene.html`（标注）+ 截图 + 校验输出。

### 3.9 D3 ｜④ 三维 Blender ｜材质贴图

**要做什么**

给关键材质加贴图。

**为什么**

`模型升级路线图.md` 第 1 条写过：**glb 里 `images: 0`、`textures: 0`，12 个材质全是纯色**（`不锈钢.013`、`泵体蓝.001`…）。**这是"塑料积木感"的头号来源。**

**怎么做**

- 优先级：**不锈钢 → 泵体 → 电机 → 混凝土**（地面/基座），其余可不动
- 不锈钢要有拉丝或磨砂感；混凝土要有粗糙颗粒感
- **贴图要小**：每张控制在 200KB 内，全套别超 2MB。现在 glb 是 799KB，而验收 **1-2 要求加载 ≤3s**，贴图一爆就挂
- 用 Blender 的 PBR 材质（Base Color / Roughness / Metallic 三张图），别只贴一张颜色图——**只有颜色图还是"塑料"**

**验收标准**

1. 重新加载后不锈钢**看起来像金属**（有反射、有质感），不再是纯蓝色块
2. `泵房.glb` 体积**不超过 2.5MB**
3. 加载时间仍 **≤3s**（验收 1-2）
4. 节点名仍正确

**自测要求**：贴图前后对比截图 + glb 体积 + 加载耗时。

**交付物**：`泵房.glb`（新）+ 前后对比截图 + 体积与耗时数据。

### 3.10 D4 ｜⑤ 前端 ｜环境反射

**要做什么**

在 `scene.html` 里加 Environment / PMREM。

**为什么**

`模型升级路线图.md` 第 2 条：现在只有 Ambient + Hemisphere + 一盏 DirectionalLight（`scene.html:465-478`），**无 Environment / PMREM，所以不锈钢没有反射**。路线图里明确说这是"**简陋感的头号来源**"。

1. 金属设备表面**能看到环境反射**（转动视角时高光跟着变）
2. 加载时间仍 ≤3s
3. 帧率仍 ≥30 FPS（验收 5-3）
4. 整体色调**没有过曝或发白**

**自测要求**：前后对比截图 + FPS + 加载耗时。

**交付物**：`代码/frontend/scene.html` + 对比截图 + FPS 与耗时数据。
