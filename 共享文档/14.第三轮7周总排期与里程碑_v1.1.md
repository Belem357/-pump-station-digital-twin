## 四、关键路径与"谁卡谁"

**这是排期能不能走通的核心。三条铁律：**

```
⑥ 定契约 ──▶ ① 建点 / ② 解析 / ③ 后端 ──▶ ⑤ 前端接入
                                              ▲
④ 建模（节点名）─────────────────────────────┘
```

1. **⑥ 是路径上的第一块砖。** 地址表不定稿，①②③ 全部动不了。所以 ⑥ 的工作必须**每周前半周完成**。
2. **④ 从 W1 就开工，不等地址表。** 建模与地址表无关，并行推进。**节点名一开始就按新规范**（`pump_hi_1_body` 这种），避免返工。
3. **④ 每次重新导出 `泵房.glb` 后，必须跑这三条命令**，否则前端按节点名找不到设备、屏幕上只剩地面：

```bash
node _工具/fixGlbNodeNames.mjs 泵房.glb 泵房.glb   # 节点名对齐
node _工具/validateGlb.mjs     泵房.glb            # GLB 结构完整
node _工具/validateScene.mjs                       # 场景配置引用的节点名都存在
```

## 五、三个强制门禁

每周三演示前必须过，过不了不许上演示。

| 门禁 | 内容 | 谁负责 |
|---|---|---|
| **提交门禁** | **每周三 09:00 前，所有改动必须 push 到 GitHub。** 没提交 = 没做 | 全员 |
| **契约门禁** | 地址表定稿后，① 建点完必须用 `linkCheck.py` 全量校验，② 交叉核对一遍 | ① ② |
| **模型门禁** | ④ 每次导出模型后，三个校验脚本必须全绿 | ④ |

### ⚠️ 关于"提交门禁"为什么是硬性的

本项目从 2026-09-17 开工至今，**仓库里的每一次提交都来自组长一个人，没有任何一次组员提交**。这不是要追责，而是要解决问题：**不提交 = 别人看不见 = 无法联调 = 到演示当天才发现对不上接口。**

> **从 W1 开始，每周三上午演示前必须 push。** 哪怕只改了 10 行、哪怕还没做完、哪怕代码是半成品——**先提交，再继续**。分支用 `main` 即可，不强制开分支。

## 六、技术回退方案（改崩了要有退路）

三压改造要把水泵 **2 → 6 台**、测点 **15 → 39**、线圈 **5 → 13**，六个角色的活全都要动一遍。**风险不来自方案本身，而来自改动面——任何一个环节卡住，整套系统都可能跑不起来。** 所以动手之前先存一个"确认能跑"的版本当退路。

| 时机 | 动作 |
|---|---|
| **W1 第一天** | 给当前版本打 git tag：`git tag -a v2-2pump-stable -m "说明" && git push origin v2-2pump-stable` |
| **改造过程中** | 哪一步卡住，就 `git switch -c 回退演示 v2-2pump-stable` 从 tag 拉一个分支，先保证手里始终有一个能跑的系统可用于演示 |
| **W7 答辩前** | 准备两套演示：主方案（三压 6 泵）+ 回退版本（2 泵版）。**若改造到答辩前仍未稳定，就切 tag 演示 2 泵版**——这是技术兜底，不是另一套方案 |

**打 tag 是 W1 的第一件事，先于任何代码改动。** tag 只保证"代码能退回去"，与项目范围大小无关。

## 七、三压分区的定位与设计依据

三压六泵**是按真实小区泵房的实际做法定的**，依据来自现场视频（B 站《供水机房参观，供水系统及设备讲解》），不是凭空设计。

**设计依据**：楼宇分区供水——18 层住宅按高中低三区分别加压是标准做法。高区扬程最大、低区最小，一套泵打全楼既费电又难稳压，分区之后每区各自恒压，这才是真实泵房的运行方式。

**项目定位**：这是**单个泵房内部的分区结构**，区别于 PRD 第 4 节明确排除的"多泵房/多站点集中管理"。**属于单站深化，不是多站扩张。**

被问到范围时，按上面两段答即可：设计依据是真实工程做法，定位是单站内的深化。
